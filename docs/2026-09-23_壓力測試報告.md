# 700 人同時演練壓力測試報告（2026-09-23）

## 結論

- **目前預設（佇列 6 個 worker）：不可行。** 700 人只有 45 人（6%）完成一場演練，570 人連開場都等不到（排隊超過 60 秒 → 「系統忙碌」）。
- **80 個 worker：可行但偏慢。** 700 人 100% 完成、零失敗，但每句對話中位數要等 8.7 秒，最慢的一成要等 20 秒以上。
- **150 個 worker：可行而且順暢（Anthropic 上限足夠時的建議值）。** 700 人 100% 完成、零失敗，每句對話中位數 3.9 秒，幾乎等於 Claude 本身的回應時間，最多只有 51 筆在排隊。
- 伺服器本身（Flask＋佇列）在所有測試中都沒有卡住：查詢佇列狀態都在 0.03 秒內回應、伺服器零錯誤、記憶體約 250 MB。**瓶頸是「同時能跟 Claude 對話的數量」（worker 數），這只要改設定值就能調整。**
- **真的 Claude 50 人實測：100% 完成、零錯誤**，每句對話中位數 3.9 秒。換算 700 人約需 RPM 2,100／ITPM 220 萬／OTPM 62 萬。
- **Anthropic 上限決定成敗**：Scale 級（10,000／1,000 萬／200 萬）→ 700 人可行；Console 畫面上的 1,000／50 萬／8 萬 → 只夠約 90 人。需確認哪一組實際生效，並把佇列的 RPM／ITPM 調到上限的 9 成。

> ⚠️ 700 人測試用「假 Claude」（照真實回應時間等待、不打 API、不花錢），證明的是**我們的伺服器與佇列撐得住**。
> 另以**真的 Claude 跑 50 人**：100% 完成、零錯誤，回應時間與 token 用量與假 Claude 的設定相符。

## 真實 Claude 實測：50 人同時（2026-09-24）

用真的 Claude API（claude-haiku-4-5）在本機跑 50 人，流程與上面相同（開場＋6 句對話＋點評），6 句台詞改為實際的勸阻對話。
佇列設定照 `render.yaml`：150 workers、RPM 800、ITPM 36 萬。使用獨立測試資料庫，未寫入正式資料。

| 項目 | 結果 |
|---|---|
| **完成整場演練** | **50 / 50（100%）** |
| 第一次送出就成功 | 開場 50/50、對話 300/300、點評 50/50 |
| Anthropic 回 429／伺服器錯誤 | 0／0 |
| 開場 中位數／90%／最慢 | 2.7／3.9／11.1 秒 |
| **對話 中位數／90%／最慢** | **3.9／4.2／14.8 秒** |
| 點評 中位數／90%／最慢 | 8.7／10.4／11.4 秒 |
| 排隊 | 從未排隊（最多同時 24 筆處理中） |
| 尖峰每分鐘請求數 | 149 |
| 伺服器 CPU／記憶體 | 14%／172 MB |

**實際 token 用量（開場＋對話，每次呼叫平均）：** 未快取輸入 656、讀取快取 5,572、輸出 189。點評平均約 700 字（約 900 輸出 tokens）。
假 Claude 的設定（對話 2–4.5 秒、點評 6–10 秒、未快取輸入每回合約 +190）與實測相符，前面 700 人壓測的結果可信。

### 依實測換算 700 人同時（線性放大 14 倍）

| 項目 | 50 人實測尖峰 | 700 人估計 | Scale 上限 | Console 畫面上限 |
|---|---|---|---|---|
| RPM | 149 | 約 2,100 | 10,000 ✅ | 1,000 ❌ |
| ITPM（不含讀取快取） | 約 16 萬 | 約 220 萬 | 1,000 萬 ✅ | 50 萬 ❌ |
| OTPM | 約 4.4 萬 | 約 62 萬 | 200 萬 ✅ | 8 萬 ❌ |

- **若 Scale 上限（10,000／1,000 萬／200 萬）已生效：700 人同時可行**，三項都有 3 倍以上餘裕。
- 若實際是 Console 畫面上的 1,000／50 萬／8 萬：約 **90 人**就會碰到 OTPM 上限。
- **佇列的 RPM／ITPM 必須跟著調高**：目前 RPM 800 會把 700 人壓在約 270 人的速度。Scale 生效後建議 `CLAUDE_QUEUE_RPM=9000`、`CLAUDE_QUEUE_ITPM=9000000`。
- ITPM 的實際用量比先前估計（130–150 萬）高，主要是點評每次要送整段對話＋評分規則，且不走快取。

**費用（依實測，Haiku 4.5 定價估算）：** 每場約 US$0.025；700 人各做前測、後測共 1,400 場約 **US$35**。

## 附帶發現：輸入 token（ITPM）會比請求次數更早碰到上限

初版測試（B、C）把每次呼叫的輸入 token 估高了約 4 倍，結果 150 個 worker 的 C 在每分鐘約 1,100 次請求時就碰到 400 萬 ITPM 上限，對話等待和 80 個 worker 差不多（中位數 9.8 秒），還有 4 句第一次送出就收到「系統忙碌」。

| | B：80 workers（token 偏高） | C：150 workers（token 偏高） |
|---|---|---|
| 完成整場演練 | 700 人 | 700 人 |
| 對話 中位數／90%／最慢 | 9.9／25.7／37.9 秒 | 9.8／25.9／55.8 秒 |
| 點評 中位數 | 27.3 秒 | 21.6 秒 |

**意義：** 對話愈長，每次要重送的歷史文字愈多，ITPM 會比 RPM 先成為限制。佇列的限流器同時看 RPM 與 ITPM，會自動把速度壓在上限內，不會讓 Anthropic 直接拒絕；但如果帳號的 ITPM 上限不夠高，加再多 worker 也沒用。

## 目前帳號上限換算：同時能服務多少人

Anthropic Console 畫面顯示的 Claude Haiku 4.x 上限（2026-09-24 提供；帳號另稱為 Scale 級 10,000 RPM／1,000 萬 ITPM／200 萬 OTPM，需確認哪一組實際生效）。「700 人同時約需」依真實 Claude 50 人實測換算：

| 項目 | 帳號上限 | 700 人同時約需 |
|---|---|---|
| Requests（RPM） | 1,000／分鐘 | 約 2,100 |
| Input tokens，不含讀取快取（ITPM） | 50 萬／分鐘 | 約 220 萬 |
| **Output tokens（OTPM）** | **8 萬／分鐘** | **約 62 萬** |

以下為實測前的初步估算（每位學員一整場：開場＋6 句對話＋點評），實測後的數字見上方「真實 Claude 實測」：

| | 每場用量 | 以壓測節奏（一場約 3.5 分鐘）換算每人每分鐘 |
|---|---|---|
| 請求 | 8 次 | 2.3 次 |
| 輸入 tokens（不含讀取快取） | 約 6,800 | 約 1,950 |
| 輸出 tokens（對話每句約 200、點評約 900） | 約 2,300 | 約 650 |

以上限的 9 成換算「同時能順暢演練的人數」：

| 限制 | 可同時服務 |
|---|---|
| RPM 900 | 約 390 人 |
| ITPM 45 萬 | 約 230 人 |
| **OTPM 7.2 萬** | **約 110 人** ← 最先碰到 |

**結論：若 Console 畫面上的上限才是實際生效的，同時演練約 90–110 人就是上限，700 人同時進行不可行。** 瓶頸是**輸出 tokens（OTPM）**，主要被點評（每次約 900 tokens）吃掉。

- 若學員實際節奏較慢（每句思考、講話更久，一場 7 分鐘），可同時服務的人數約加倍（約 220 人）。
- 目前佇列只限制 RPM 與 ITPM，**沒有限制 OTPM**：超過 8 萬時會由 Anthropic 回 429，靠 SDK 自動重試撐住，尖峰時學員會看到較多「系統忙碌」。建議佇列加上 OTPM 限流。

要 700 人同時：

1. **確認 Scale 上限已生效**（10,000／1,000 萬／200 萬即足夠）；或向 Anthropic 申請至少 RPM 2,500、ITPM 270 萬、**OTPM 75 萬**（實測換算再加 2 成餘裕）。
2. 或 **分梯次**：每梯約 90 人、共 8 梯，每梯錯開約 5 分鐘開始。

## 建議設定

| 項目 | 建議 |
|---|---|
| `CLAUDE_QUEUE_WORKERS` | **150**（已設定；80 可用但每句要等約 9 秒） |
| `CLAUDE_QUEUE_RPM` | **9000**（已設定，Scale 上限 10,000 的 9 成） |
| `CLAUDE_QUEUE_ITPM` | **9000000**（已設定，Scale 上限 1,000 萬的 9 成） |
| OTPM 限流 | 佇列尚未支援；Scale 上限下 700 人僅用約 3 成，可暫不處理；若上限是 8 萬則必須新增 |
| Anthropic 帳號 | 確認 Scale 上限（10,000／1,000 萬／200 萬）已套用到 API key 所屬的 organization，並確認每月花費上限 |
| Render 方案 | 升級到 **Standard（1 CPU／2 GB）以上**，講習結束可降回 |
| 備案 | 若上限只有 Console 畫面上的數字：**分 8 梯、每梯約 90 人** |

## 上線前待確認

1. **Anthropic 上限**：Console 畫面顯示 1,000／50 萬／8 萬（約 90 人），帳號另稱 Scale 級 10,000／1,000 萬／200 萬（700 人可行）。需確認哪一組實際生效。
2. **每月花費上限**：700 人各做一次前測、一次後測約 **US$35**（依實測），確認不會在講習當天用完。
3. **Render 方案**：本機 Mac 已用到單核約 50%，Render starter 只有 0.5 CPU 且較慢，很可能不夠。
4. **正式環境小規模實測**：本機已用真的 Claude 跑過 50 人（全部成功）；建議部署後在 Render（Standard 方案）再跑一次 50–100 人。
